Payment integrity — fix before launch

These are not feature gaps. They are defects in code that already exists, and they let people take paid products for free or leave you having captured money you never deliver against. Three independent audits found the first two items separately; both were then re-verified by hand against the source.

P0 · live · free products

One paid payment id can be replayed to unlock every future order

The payment callback does correctly call MyFatoorah server-side to confirm status, so it does not simply trust a status parameter. The flaw is which key it looks up: it prefers the caller-supplied paymentId over the id it stored itself, and then never checks that the invoice it got back belongs to the transaction being settled.

A user pays once, for the cheapest thing on the site, and can then obtain every course, book, trip package and consultation for free — indefinitely. The callback route is public and unauthenticated, and the callback URL with the paid id sits in their browser history.

Evidence

  • MyFatoorahBaseStrategy.php:127–129 — the caller-supplied paymentId takes priority over the stored payment_id (:131) and invoice_id (:135)
  • MyFatoorahBaseStrategy.php:98 — gateway queried with that caller-controlled key
  • MyFatoorahBaseStrategy.php:100,108 — only InvoiceStatus is read; 'paid' returns success
  • MyFatoorahBaseStrategy.php:42 — pay() sets CustomerReference = transaction->payment_ref, and it is never compared back
  • InvoiceValue / currency are never compared against transaction->amount
  • MyFatoorahBaseStrategy.php:104 — the foreign InvoiceId then overwrites the stored one
  • routes/Api/general.php:22 — payments/callback accepts GET or POST, no auth
  • PaymentTransactionResource.php:18 — the user is handed their own payment_ref at checkout

Attack sequence

  • 1. buy the cheapest item legitimately; keep the paymentId from the redirect URL
  • 2. start checkout on an expensive course; do not pay; note the returned payment_ref
  • 3. call payments/callback with payment_ref = the expensive one, paymentId = the old paid one
  • 4. gateway reports that invoice as Paid → order marked paid, enrollment granted, invoice issued
  • 5. reuse the same paymentId for every future purchase, of any type

Fix

  • remove the caller-supplied paymentId branch — trust only the stored payment_id / invoice_id
  • require CustomerReference === transaction->payment_ref before returning success
  • require InvoiceValue (and currency) to match transaction->amount before returning success
P0 · latent · free products

An unrecognised payment driver silently becomes a fake “always succeeds” gateway

The strategy factory falls back to SimulatedPaymentStrategy for any driver it does not recognise, and that simulator returns success by default with no gateway call and no money. Only three drivers are mapped. The admin dashboard accepts the driver as free text with no allow-list, so a single admin action — adding “cash”, “tabby”, “mada”, or simply typing knet instead of k-net — turns every purchase through that method into a free one.

Not exploitable on a correctly seeded database today: the seeder creates only the three mapped drivers, so this is latent rather than live. It is one mistake away from live, and the mistake is invisible — the order simply says “paid”.

Separately and more urgently: simulate_result is a client-supplied, validated field on eight checkout and booking endpoints, with no environment guard anywhere in the codebase. It only takes effect through the simulator, but it means the simulated path is directly reachable from the public API rather than test-only.

Evidence

  • config/payments.php:15 — default_strategy => SimulatedPaymentStrategy::class
  • config/payments.php:18–20 — only visa-mastercard, k-net, apple-pay are mapped
  • PaymentStrategyFactory.php:16–17 — unknown driver falls back to the default strategy
  • SimulatedPaymentStrategy.php:13–20 — pay() returns success by DEFAULT (no meta required)
  • SimulatedPaymentStrategy.php:22–31 — handleCallback trusts payload['status'] === 'success' verbatim, over the unauthenticated callback
  • Dashboard/PaymentMethods/StoreRequest.php:30 — driver is free text; no Rule::in
  • PaymentMethodSeeder.php:14–23 — seeds only the three mapped drivers (hence latent)
  • simulate_result accepted in 8 request/controller pairs; no app()->environment() guard anywhere

Fix

  • throw  on an unknown driver instead of falling back — remove default_strategy
  • add   Rule::in(array_keys(config('payments.drivers'))) to the dashboard driver field
  • gate  simulate_result to local/testing environments only
P0 · undercharging

A currency-rate outage silently charges base-currency numbers

When every exchange-rate provider fails, the converter logs a warning and returns a rate of 1.0 rather than failing the checkout. The amount is then persisted and is exactly what the gateway charges. The default provider returns nothing when its API key is unset, and failures are not cached, so every request during an outage underprices.

A 10 KWD course is charged as 10 USD (≈3.25 KWD) or 10 SAR (≈1 KWD). Silent — a log line is the only signal.

Evidence

  • CurrencyConverter.php:29–40 and :63–72 — returns rate => 1.0 on total provider failure
  • CurrencyConverter.php:181 — default 'exchangerate' provider returns null with no API key set
  • the 'frankfurter' fallback provider does not carry KWD at all
  • MyFatoorahBaseStrategy.php:160–163 — gateway is charged the persisted amount

Fix

  • fail the checkout when no rate resolves and the target currency isn't the base currency — never fall back to 1.0
P1 · money taken, nothing delivered

Any error during fulfilment rolls back the payment record but not the payment

Fulfilment runs inside the same database transaction as the write that marks the payment successful. If anything throws after the gateway has captured the money, the success write is rolled back too — leaving money captured, no order, no entitlement, no invoice, and no record that anything happened. There is no reconciliation job anywhere to detect it.

The customer is charged and receives nothing, and the system does not know. Three concrete triggers are already present in the code.

Triggers found

  • TripPackageOrderService.php:242–253 — last-seat race throws inside processResult's transaction (:163–171), reverting the SUCCESS write
  • InvoiceService.php:27–33 — invoice number computed as max(id)+1 with no lock against a unique column; concurrent buyers collide and the loser's exception aborts fulfilment
  • InvoiceService.php:43–57 — QR PNG generation runs inside the fulfilment transaction and needs imagick/GD; if it is unavailable every paid callback throws

That third trigger is not hypothetical: imagick is absent from at least one environment in this project — it is why 33 of the backend tests error out on the machine this audit ran on. On a server without it, every single payment would capture money and deliver nothing.

Fix

  • commit the SUCCESS status in its own transaction, before fulfilment
  • catch  fulfilment failures and record meta.fulfillment_status = 'failed'
  • move  QR generation after commit and let qr_code_path stay null on failure
  • add   a reconciliation command for SUCCESS-without-entitlement and PENDING-with-paid-gateway-status
  • lock  the invoice number counter, or catch the unique violation and retry
P0 · money taken, order never completes

There is no server-to-server webhook and no reconciliation

The only way a payment is ever confirmed is the customer's own browser being redirected back. CallBackUrl and ErrorUrl are set to the same browser-redirect URL — there is no separate server-to-server webhook, and no scheduled job ever revisits a pending transaction.

A customer who pays and then closes the tab, loses signal, or has their browser drop the redirect stays pending forever — money captured by the gateway, no enrollment, no invoice, and nothing anywhere that notices. This will happen routinely on mobile, not rarely.

Evidence

  • MyFatoorahBaseStrategy.php:26–28,40–41 — CallBackUrl and ErrorUrl are both the same browser redirect to payments/callback
  • routes/console.php:22–26 — scheduler runs only ExpireSubscriptions, CompleteEndedCareBookings, SendCareBookingReminders; nothing touches PaymentTransaction
  • Modules/Payment/Gateways/MyFatoorahGateway.php:36 — GetPaymentStatus already exists, so the query side is available

Needed

  • register a real server-to-server webhook with MyFatoorah, separate from the browser redirect
  • add     a scheduled reconciliation command that re-queries pending transactions and settles or fails them
P1

An abandoned payment locks a user out of that doctor permanently

A booking is created in pending_payment before the user pays. Nothing ever transitions it out of that state on failure or abandonment — the EXPIRED and CLOSED enum cases are, like CANCELLED elsewhere, unreachable: nothing in the codebase ever sets them. But the "do you already have an open booking" check counts pending_payment as open.

A user who starts a booking and doesn't finish paying gets can_book: false for that doctor forever, and re-booking throws "already booked". There is no way out for them or for an admin. Slots are not held, so this is a lock-out rather than a slot leak.

Evidence

  • CareBookingService.php:982 — bookings are created with status PENDING_PAYMENT
  • CareBookingService.php:433–438 — PENDING_PAYMENT returns can_book => false
  • CareBookingService.php:1594–1597 — findOpenInitialConsultationBooking counts PENDING_PAYMENT as open; :1536–1540 throws already-booked
  • CareBookingStatusEnum EXPIRED — zero references outside the enum; CLOSED appears only in a model scope list (Models/CareBooking.php:174)
  • processResult on a FAILED payment updates only the transaction, leaving the booking in PENDING_PAYMENT

Needed

  • transition the booking to failed/expired when its payment fails
  • add       an expiry job for abandoned pending_payment bookings, and make EXPIRED / CLOSED reachable
P1

Physical book orders are paid and then never fulfilled

A book order's lifecycle ends at paid. There is no shipping state, no tracking field, and no admin action to advance an order — the dashboard offers only list and view. The frontend already expects three fulfilment states that the backend has no way to express.

Nobody can mark a book as shipped or delivered, and the customer can never see where their order is. For a store selling physical books this is the whole post-purchase experience.

Evidence

  • BookOrderStatusEnum — pending, paid, failed, cancelled; no shipping states
  • migration 2026_06_25_000003 — book_orders has shipping_address_snapshot but no shipping status or tracking number
  • routes/web.php:505 + Dashboard/BookOrderController.php — index and show only; no status-change action
  • frontend src/features/books/types/book-purchase.types.ts:4,30 expects 'purchased' | 'shipped' | 'delivered'

Needed

  • migration fulfilment status + tracking number on book_orders
  • admin    an action to advance an order to shipped / delivered
  • expose   that status on the existing my-books endpoints
P1

Replaying a callback resurrects a finished consultation

The replay guard only short-circuits for bookings in confirmed or pending_slot. A scheduled command moves finished bookings to completed every minute — after which replaying the old callback URL pushes the booking back to confirmed and re-opens its chat room. Repeatable, and closed and expired bookings resurrect the same way.

A second consultation for a single payment, on demand.

Evidence

  • CareBookingService.php:689–698 — guard covers only CONFIRMED / PENDING_SLOT
  • CareBookingService.php:733–744, 1024–1034 — status written back to CONFIRMED
  • routes/console.php:25 — care-bookings:complete-ended runs every minute

Fix

  • short-circuit whenever the transaction is already SUCCESS and a booking exists in any status other than pending_payment

Worth fixing at the same time as cancellation: the paid-order guards elsewhere test for === PAID, so the day a cancel or refund feature lands, replaying a callback will restore the cancelled entitlement.

POST platform-reviews calls auth('sanctum'), but no sanctum guard is defined — only admin and user — so Laravel throws and the endpoint 500s on every call. This is the same class of bug as the address-book import failure documented further down, and both are one-line fixes.

Evidence

  • Api/General/PlatformReviewController.php:37 — auth('sanctum')->user()
  • config/auth.php:38–47 — guards are 'admin' and 'user' only; no 'sanctum'
  • a quick way to confirm the address bug: `php artisan route:list` fails outright with “Class UserAddressController does not exist”. Note route:cache still succeeds, so a deploy will not catch it.

P2 · hardening

Disclosure and robustness items worth closing while you are in here

  • Invoices are public and permanent. Invoice/routes/web.php:6–10 — /invoices/{uuid} has no auth, no ownership check and no expiry; the page carries customer name, email, phone and amounts, and a PNG copy is cached inside the webroot. Not enumerable (UUIDv4) and it looks deliberate, since the QR encodes this URL — but if “shareable link” is the intent, decide it explicitly rather than by accident.
  • Exception handlers leak internals on every api/* route regardless of app.debug — bootstrap/app.php:135–146, :226–237, :279–316 return the exception message plus absolute file paths, including raw SQL errors.
  • The API rate limiter is effectively per-IP, not per-user — RouteServiceProvider.php:43 keys on $request->user(), which resolves the default admin guard before auth:user has run.

  • The slot lock is single-node — Cache::lock with the file cache store; pin it to redis or the database before running more than one app server.
  • subscriptions/plans/{id} omits the active scope that the list endpoint applies, so inactive plans are readable by id. Disclosure only — checkout still validates status.

The tests do not cover the real payment path at all

This is why none of the above was caught. The payment-method factory generates a random driver slug, which is never one of the three mapped drivers — so every payment test silently exercises the fake simulator, not the real gateway. No test anywhere issues a request to payments/callback. The suite passing tells you nothing about whether payments work.

Evidence

  • consequently the defects above sit entirely outside test coverage

Also worth knowing about the suite as it stands

  • 387 tests ran: 81 failures and 4 errors — but these are environmental, not code defects
  • 33 stem from the imagick PHP extension being absent (see the fulfilment-rollback item — that absence is itself a production risk)
  • 50 are dashboard tests requesting /en/admin/... while routes register under the default locale ar, because routes/web.php:89 builds its prefix from LaravelLocalization::setLocale() at registration time

Fix

  • point the factory at a real mapped driver, and add callback tests covering replay, foreign paymentId, and amount mismatch
  • install imagick in CI and on servers, or make QR generation optional
  • fix   the locale prefix so the dashboard tests address the registered routes

P0 · blocker

This is not missing code — the controller is complete. routes/Api/user.php:180 references UserAddressController::class, but that file never imports the class and carries no namespace declaration, so ::class resolves to \UserAddressController in the global namespace. Because ::class on an unimported name is a compile-time string constant, route registration and route:cache both succeed — the failure appears only at dispatch, as “Target class [UserAddressController] does not exist.”

Checkout cannot collect or select a shipping address, so physical book orders cannot complete.

Evidence

  • routes/Api/user.php:180 — prefix('addresses')->controller(UserAddressController::class)

  • UserAddressController.php:19,35,58,83,99 — index, store, update, setDefault, destroy all present and implemented

P1 · unsized

Nothing can be cancelled or refunded, anywhere

There is no cancellation, refund or reschedule endpoint in the entire codebase — not in the API, and not in the admin dashboard. Once a user pays for a course, a book, a booking or a subscription, neither they nor an administrator has any way to undo it. The payment module has no refund capability at all.

The evidence says this was intended and then left unbuilt, not deliberately excluded: BookOrderStatusEnum and CourseOrderStatusEnum both define a CANCELLED case, and nothing in the codebase ever sets it — it is an unreachable state.

A subscriber cannot cancel a subscription. Depending on your payment provider's rules and local consumer law, that may be a compliance problem and not merely a missing feature — worth checking before launch.

Evidence

  • no cancel / refund / reschedule route in routes/Api/user.php or general.php (the only web.php matches are newsletter and scheduled notifications)
  • BookOrderStatusEnum · CourseOrderStatusEnum — define CANCELLED; no code anywhere assigns it
  • CareBookingStatusEnum — pending_payment, pending_slot, confirmed, completed, closed, expired; no cancelled state exists at all
  • SubscriptionStatusEnum — active, expired only; no cancelled state
  • app/Modules/Payment/ — zero references to refund; MyFatoorahGateway has no refund path
  • frontend has no cancellation UI either, so this was never built on either side

Needed — but answer the policy question first

  • decide what is cancellable, within what window, and whether money is returned or credited to the wallet
  • then   a cancel endpoint per cancellable flow, a cancelled state where the enum lacks one, and a refund path in the payment module
  • min    subscription cancellation is the one to treat as non-negotiable

Deliberately left unsized: the endpoint count depends entirely on the policy. If refunds go to wallet credit rather than back to the card, this becomes considerably cheaper — which is a good reason to settle the wallet work at the same time.

Discount codes exist in the checkout UI and nowhere else

The checkout page applies a hardcoded SAVE10 for 10% off (src/features/checkout/components/checkout-page.tsx:222–236). There is no coupon, promo or discount concept anywhere in the backend — no table, no column, no validation.

Either discount codes are a real feature, in which case they need a table, admin CRUD, and server-side validation applied at checkout where the price is computed — or the field should come out of the UI before launch, because today it is a discount the server knows nothing about.

Flagging as a decision rather than a ticket. Note that if it is built, the price must be recomputed server-side: the audit confirmed no client can currently supply an amount, and a coupon implemented client-side would be the first crack in that.

Deliberately not being built

Recorded so it doesn't get picked up by mistake later. This was decided, not overlooked.

No JSON admin API. The Next.js app contains 24 admin pages running on localStorage, and making them real would take an estimated 55–65 endpoints. Every one of those entities — books, clinics, courses, trips, users, podcasts, consultations, encyclopedia, community, newsletter, schedules, assistant settings — already has full CRUD in the Laravel Blade dashboard. The duplication is total: not one admin page manages anything the dashboard does not already cover.

Decision: admin stays in the Laravel dashboard. The Next admin pages will be removed. This is frontend cleanup and costs the backend nothing.

Carve-out when deleting: the doctor portal pages under src/app/(doctor)/ render components that live inside src/features/admin/ — doctor-appointments-page.tsx and doctor-appointment-detail-page.tsx. Deleting the admin feature wholesale would take the doctor portal with it, and the doctor portal is being kept.

What this does not cover

Stated plainly, because this document is being handed over as a definition of remaining work and it would be easy to read it as more than it is.

  • Nothing was executed. Every finding comes from reading the code. An endpoint was counted as working if the route exists and its controller method exists and is not a stub — an endpoint that exists, has a real body, and returns wrong data or fails on an edge case would pass every check here. “Implemented” is not the same as “correct”.
  • Business logic inside working endpoints was not verified. Route shapes and response fields were compared; the rules behind them were not. Whether installment pricing computes correctly, or slot availability honours breaks and closures, is untested by this audit. The one such rule that did surface — the package session interval — was found only incidentally.
  • The backend test suite was not run. No statement here is backed by a passing test.
  • Non-functional concerns are out of scope — performance, N+1 queries, rate limiting, and the security of the endpoints themselves were not assessed.
  • Arabic / localisation completeness was not checked per field, beyond confirming the locale middleware and that resources return localised strings.

What it does cover, and covers exhaustively: every route was enumerated and every referenced controller action confirmed to exist and be non-empty; every frontend API call was diffed against those routes; every API resource was compared field-by-field against the frontend types consuming it; every mock-backed frontend feature was checked against backend capability; and every table and model was checked for route exposure.

Method — every route in routes/api.php, routes/Api/user.php, routes/Api/general.php and routes/web.php was enumerated and each referenced controller action opened to confirm it exists and is not a stub. Frontend calls were extracted from every service under src/features/** and diffed against that inventory; all 10 initially unmatched calls proved to be normalisation artefacts rather than gaps. Backend Resource classes were then compared field-by-field against the frontend types and components that consume them, and every mock-backed frontend service was checked to see whether the backend could serve it today.
Claims from the repo's existing audit documents were re-verified against the live route files rather than taken at face value; three were stale. Every finding then went through a second independent pass against the same code, which corrected three of them — push delivery and healing stories were both scoped far too broadly in the first draft, and the group-chat item overstated its impact. The endpoint figures and both P0s survived that pass unchanged.
